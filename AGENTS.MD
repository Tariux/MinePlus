Mineplus is a Spigot/Paper plugin focused on a data-driven "vanilla-like systems" framework: custom items, managed blocks, multiblocks/machines, recipes, GUIs, and virtual rendered models, all server-side (no client mod required).

Runtime starts in `MineplusPlugin`: it loads `settings.mp.yml` via `ConfigManager`, applies `VirtualRenderingSettings` to `VirtualBlockManager`, loads model assets from the plugin data folder, then bootstraps `PluginContext`. `PluginContext` wires `ItemRegistry` and the infrastructure engine + `InfrastructureApi`.

The modern extension core is `InfrastructureEngine`. It composes:
- `MultiBlockRegistry` (type registry + instance indices by UUID/location)
- `MultiBlockLifecycleManager` (create/place/interact/upgrade/remove/tick, model reload, save/restore)
- `ModelRenderingManager` (maps multiblock level -> virtual model spawn/swap/remove through `VirtualBlockManager`)
- `MultiBlockLinkingSystem` + `HookBus` (block links, signals, lifecycle event fanout)
- `RecipeManager`, `UpgradeManager`, `InfrastructureGuiManager`, and persistence/config loaders.

Feature definitions can come from code or JSON:
- Code: use `InfrastructureApi` (`registerMultiBlock`, `create/place/upgrade/remove`, `registerHook`, lifecycle listeners, recipe/gui registration, linking/signals).
- JSON multiblocks: `plugins/Mineplus/multiblocks/*.json` parsed by `MultiBlockConfigLoader` into `MultiBlockType` + `MultiBlockLevel` (`model`, `speed`, `durability`, `upgradeCost`, `guiOptions`, optional `gui` key).
- JSON machine recipes: `plugins/Mineplus/recipes/*.json` parsed by `RecipeConfigLoader` into `MachineRecipe`.

Virtual rendering pipeline (`infrastructure.virtual`):
- `BbModelImporter` single-pass streaming parser (Gson `JsonReader`): `.bbmodel` -> `VirtualModel`. Dead branches (texture `source` Base64 PNGs, animations, timeline setups) are skipped with `skipValue()` and never allocated. Captures `resolution` and per-element `light_emission`; preserves negative-coordinate geometry and outliner pivot-conjugation transforms.
- Anchor convention (`ORIGIN_MODE`, default `CENTER`): vanilla/Blockbench space — pixel (0,0,0) is the anchor block's center at its base (a full block spans pixels [-8..8] xz, [0..16] y). Single-block models occupy exactly one block and rotate about the block center. `GRID` (corner anchor) is available for multi-block structures; `LEGACY` is an alias of `CENTER`.
- `RotationSnapper` snaps placement rotations to the 24 orientation-preserving signed axis permutations, giving exact integer cell-lattice transforms; deviations beyond the threshold are warned via `DebugLogger`.
- `GeometryOccupancyCalculator` geometry-aware collision: per-cube SAT cell rasterization (axis-aligned fast path), `GEOMETRY` (default) / `SURFACE` (interior hollowing) modes (`AABB` is a compat alias resolved through the geometry path), fastutil `LongOpenHashSet` cells packed as 26/26/12-bit X/Z/Y sign-extended longs (overflow-safe near world borders), per-(model, orientation, mode) cache, and `ThreadLocal` scratch vectors so the rasterization loop is allocation-free. Cell rasterization consumes the exact same `T(anchorOffset)·R·M` transform the displays use, so barriers and visuals cannot drift.
- `TextureMaterialResolver` filename->vanilla-material pipeline (curated map -> direct match -> suffix-strip -> aliases -> fuzzy -> fallback) with a JVM-lifetime cache; unresolved names are reported per model (`/mineplus model info`).
- `DisplayEmitter` per-cube emission: fast path = one `BlockDisplay` per uniform cube; mixed-material cubes add thin per-face plates (box mapping parity, UV in-plane rotation, `light_emission` -> brightness).
- UV alignment layer: `FaceUvAnalyzer` inspects each `BakedFace` UV window (sub-region, half, wrap, flip, rotation) and `OrientableBlockStates` renders it — half-texture windows via slab-type crops with geometry compensation; wrapping windows via native-density tile grids (one display per texture tile, no stretching); directional materials get `facing`/`axis` block states so fronts/rings/lines land on the referencing face; full windows render the complete texture. `/mineplus model info` reports per-face UV diagnostics; arbitrary sub-pixel crops need a client resource pack and are out of scope.
- Texel surface baking (`infrastructure.virtual.texel`): decomposition of a face's UV window into per-pixel texels quantized to the flat vanilla palette, merged into maximal same-color rectangles (`TexelMerge`, greedy meshing) that render as thin plates. Baking runs asynchronously (`CompletableFuture` off the main thread, guarded by a bake-generation counter so results superseded by a reload/settings change are discarded; spawn paths wait — bounded — for a model's in-flight bake so restored/reloaded instances never render without their texel textures). `TexelSampler` is the single UV→PNG bridge both bakers share — window + in-plane-rotation affine precomputed into six coefficients over a bulk-extracted ARGB raster (`TextureImageStore.raster()`), so sampling is allocation-free primitive arithmetic; flipped windows sample mirrored; alpha < 128 is cutout. `TexelPalette` = 66 visually-flat blocks (16 concretes, 16 concrete powders, 16 terracottas, snow, and 18 flat stones/minerals — polished granite deliberately excluded as too conspicuous) with Oklab perceptual matching (lightness-weighted, Minecraft directional-shade compensated), a bounded match cache, and near-match tie-breaking; only pure-flat concretes and snow are stretchable — powders, terracottas and stones stay 1×1. Occlusion culling probes each texel's exact plate position against other cubes' oriented boxes (scratch vectors, no per-probe allocation); center-occluded texels are rescued when any footprint corner is visible (label-band overhangs). Enclosed-transparency infill flood-fills from the grid rim: rim-reachable transparency is genuine cutout, enclosed transparency (atlas padding) takes the majority palette entry of its opaque 4-neighbors. Supersampling accumulates alpha-weighted color; texels under half coverage emit nothing. Plates are 1/1024-block thin and inset in-plane by one plate thickness at every face edge, so perpendicular plates sharing a cube edge are geometrically disjoint — they touch exactly instead of interpenetrating, regardless of how thin the client renders them. Budgets: per-face and per-instance plate ceilings (`TEXEL_BAKING` settings, meta overrides) with legacy-tier fallback per face — a budget-fallback face whose texture name resolves to no vanilla material plates its cube's dominant baked palette color instead of the resolver's concrete-white fallback, so partially baked models degrade to a flat local tone, never white.
- `ModelMeta` per-model overrides via `models/<key>.meta.json` (`textureMode`, `originMode`, `collisionMode`, `autoplay`, `texelMode`, `texelDetail`, `maxTexelPlatesPerFace`, `maxTexelPlatesPerInstance`, `texelBrightness`).
- Animation engine (`infrastructure.virtual.animation`): `BbModelImporter` parses `animations` in the same streaming pass (clips, bone animators keyed by outliner group name, molang-tolerant keyframes; splines sampled linear, effect animators skipped). `VirtualModel` carries the preorder bone graph (outliner groups, parent indices, pivots) + clips; `BakedCube.boneIndex` binds cubes to their innermost group. `AnimationEvaluator` samples tracks (clamped lerp/step) and composes hierarchical delta matrices `world[bone] = world[parent]·T(p/16)·R(Δr)·S(Δs)·T(-p/16)·T(Δt/16)` (Rz·Ry·Rx Blockbench Euler order, additive per-channel clip blending). `ModelAnimationManager` ticks controllers off `VirtualBlockManager.activeBlocksView()` — spawns self-attach, removals self-clean, autoplay (level `animations` key > meta `autoplay`) fires once per rendered id and never overrides explicit control. Scheduling is Folia-aware (`GlobalRegionScheduler` when RegionizedServer is present, standard scheduler otherwise), instances with no viewer inside the transport's full-LOD range and looking toward the model (~70° cone) skip their pose push, and the pose loop works in `ThreadLocal` scratch matrices/deltas (grown on demand past 256 bones) so steady-state ticks allocate nothing. Displays get `T(pivotFix)·R·boneDelta(t)·restLocal` via `setTransformationMatrix` with client-side `setInterpolationDuration`, so motion renders at the client frame rate (the server cannot push faster than its tick loop; `TICK_INTERVAL_TICKS: 1` is the max-rate default). Selector API: `AnimationApi` (`playAnimation/stopAnimation/pauseAnimation/resumeAnimation/triggerAnimation/setAnimationEnabled/getAnimations/getBones/getAnimationState`) with `AnimationSelector.animation/bone/all`; `MultiBlockHook.onAnimationStart/onAnimationComplete` fire through the isolated bridge implemented by `MultiBlockLifecycleManager`. `ONCE` clips remove controllers and return to rest; `HOLD` freezes the end frame; paused/completed controllers push no packets.
- Display transport (`infrastructure.virtual.display`): pooled virtual entity streaming (`EntityPoolManager` reuses real-but-never-spawned display entities, fastutil id index, LIFO idle pools per world) with viewer tracking, LOD tiers, and packet bundling; `ReflectionNmsAdapter` resolves every NMS constructor/method once into cached `MethodHandle`s/`Constructor`s at startup (mojang- and spigot-mapped worlds probed structurally/semantically; craft classes resolved for both versioned and unversioned CraftBukkit packages), so hot paths only pay for `invoke`. `VirtualBlockManager` falls back to plain `BlockDisplay` spawning when the transport is not running.
- `VirtualBlockManager` spawn/remove, barrier placement, spawn-area policy (`prepareSpawnArea`: creative/op placements clear non-air occupants; standard players require an empty area and get an "insufficient space" message via `MultiBlockLifecycleManager.place`), ghost `BlockDisplay` cleanup on chunk loads. All model/meta/bake/active-block state lives in `ConcurrentHashMap`s so async texel bakes and the main thread never contend. `ModelRenderingManager` resolves per-level model paths and binds rendered model IDs back to instances.
- Persistence (`infrastructure.persistence`): SQLite behind a single-connection HikariCP pool (`SqliteConnectionFactory`, WAL/NORMAL/foreign-keys/busy-timeout datasource properties, closed on shutdown); `PersistenceFacade` stages snapshots through an async write-behind queue (incremental upserts/deletes on hot paths, full replace on bulk paths).

- Resource pack system (com.mineplus.pack, Phase 2): the peer rendering axis to the virtual engine. PackApi (via PluginContext.packApi(), never null � a safe fallback when disabled keeps item identity registering with vanilla visuals) registers custom content: PackItemDefinition (implements the existing ItemDefinition, so ItemRegistry PDC identity and recognition apply unchanged) backed by a vanilla material and a registered virtual model key; model/texture assets auto-attach from the existing model/texture systems (the same PNGs the texel baker reads) during the reload-driven recompile. PackCompiler compiles the namespaced PackAssetRegistry (assets keyed by their zip entry path � an item definition and its geometry model legitimately share the asset id namespace:item/<id> but write different entries; same-entry re-registration with identical content is a no-op, same-entry different content is a genuine conflict, owner-tracked, conflict-rejecting) deterministically into hash-named packs/mp-<hash>.zip artifacts (fixed entry order/timestamps; per-asset content-hash memoization; graph hash includes pack format + item representation); PackCache prunes old artifacts (and recovers real metadata from cached zips). PackDeliveryService (LOCAL byte endpoint via JDK HttpServer / STATIC_URL / DISABLED; defaults ENABLED+LOCAL, per-player URL resolution � loopback for same-machine clients, then server IP/connect hostname/LAN address � automatic port probing when busy, never serves a URL for a dead endpoint) and PackPlayerTracker (player pack states UNKNOWN?REQUESTED?ACCEPTED/DECLINED/FAILED?APPLIED) deliver; players online when a new artifact compiles are auto-pushed (declined players respected). pack.mcmeta declares a generous supported_formats range so newer clients accept the pack; model texture references and texture assets share one last-segment path normalization (TextureAsset.normalizePath) so models and textures can never disagree inside the artifact. Backend selection is the single choke point: multiblock levels declare enderBackend: virtual|pack|virtual+pack (default virtual; RenderBackend lives in infrastructure.render), ModelRenderingManager routes � PACK levels spawn collision through VirtualBlockManager.spawnCollisionModel/estoreCollisionForState (public collision-only paths of the same lattice) and visuals through PackModelRenderer (ItemDisplay entities under their own mineplus_packdisplay: tag, swept on reconcile/chunk-load); the block primitive is a second kind on the same pack backend: a level's "renderKind": "block" routes visuals through PackBlockRenderer (one BlockDisplay per instance carrying an allocated visually-inert carrier state, Tag mineplus_packblock:, swept on reconcile/chunk-load), with the level's geometry serialized as a block-space element model (ModelJsonWriter.writeBlock) and the carrier's complete vanilla state table emitted as generated host files by BlockStateWriter (assets/minecraft/blockstates/<carrier>.json: every vanilla state preserved, only the allocated state redirected; shipped carrier PackBlockCarrier.NOTE_BLOCK, whose uniform model + client MODEL render type is what lets a BlockDisplay draw the override � INVISIBLE-render-type blocks like light/structure_void/barrier can never carry a display; allocatable states enumerate at runtime from the server's own note-block data and draw only rare mob-head-note states so unallocated/packless play renders a normal note block). Pack blocks register through PackApi.registerBlock(PackBlockDefinition) (render key = the derived <typeId>_lvl_<level>; geometryModelKey = the loaded model file stem the assets attach to) and are placed/collision-owned/persisted by the ordinary multiblock lifecycle, so texel and virtual internals stay untouched; pack-unavailable models and disabled subsystems degrade to virtual in one place. Modern 1.21.4+ items use the additive item_model component (reflection-applied); legacy servers use stable per-id custom_model_data predicates. The pack subsystem owns bounded executors, never touches the display transport/texel pool/VBM internals/animation loop, and PACK.ENABLED: false leaves the plugin byte-identical to pre-pack behavior. /mineplus pack <status|recompile|push> (status prints the resolved download URL + SHA-1). `npm run pack` in the repository builds the MineplusGun module's framed weapon assets into dist/mineplus-resource-pack.zip for manual distribution when the LOCAL endpoint is unreachable; the Core artifact stays the complete pack because every module registers into the same PackAssetRegistry. See docs/pack-system.md for the full contract and current limitations (rotated cubes serialize as AABBs, legacy host-file conflicts).
Configuration and logging:
- `ConfigManager` auto-generates `plugins/Mineplus/settings.mp.yml` on first start; the `VIRTUAL_RENDERING` section controls collision mode/epsilon/non-air policy, rotation snapping, per-face rendering, texture mode, and origin mode; `TEXEL_BAKING` controls the texel surface baker (mode/detail/plate budgets/grid edge). The `ANIMATION` section controls the animation runtime (`ENABLED`, `TICK_INTERVAL_TICKS` default 1, `INTERPOLATION_TICKS`, `AUTOPLAY`). The `PACK` section (defaults `ENABLED: true`, `DELIVERY.MODE: LOCAL` � the optimal out-of-the-box state; per-player URL resolution makes single-player/LAN and remote setups work without manual URLs) controls the resource pack subsystem. `UPDATE_CHECKER.RESOURCE_ID` (default `0` = off) gates an optional SpigotMC version check (`util/UpdateChecker`) that runs once on enable, async. The `BALLISTICS` (`ENABLED`, `MAX_ACTIVE_ROUNDS` 128, `TRACERS`, `INTERVAL_TICKS` 1), `PARTICLE_FX` (`CRITICAL_PER_TICK` 96, `AMBIENT_PER_TICK` 128, `MAX_PER_EMIT` 32) and `MOB_BEHAVIOR` sections tune the shared runtime services; all three are lazy and cost nothing until a module uses them.
- bStats metrics are always enabled (plugin id 33702) via the vendored bStats sources relocated to `com.mineplus.bstats` in `src/main/java/com/mineplus/bstats` (bstats-bukkit 3.2.1, MIT, vendored from Maven Central sources jars; relocation is required — `MetricsBase.checkRelocation` refuses to start under the original `org.bstats` package; opt-out lives in `plugins/bStats/config.yml`). `libs/` stub jars are committed so external builds and CI work (paper/spigot API, adventure, joml, gson, item-nbt-api, sqlite-jdbc, HikariCP, fastutil). Runtime provisioning: fastutil, sqlite-jdbc, joml, and gson ship with the server; HikariCP is declared via `libraries:` in `plugin.yml` and fetched by the server's library loader (first start downloads it from Maven Central).
- `DebugLogger` gates all additional lifecycle, rendering, persistence, and linking logs behind `ADDITIONAL_DEBUG_LOGS` (default `false`). When disabled, only essential plugin lifecycle logs are emitted.
- `/mineplus model info <key>` reports cube count, display estimate, resolved texture table, occupancy cells with ASCII layer dumps, texel grid histogram/palette/budget verdict, and cache status.

Current architecture direction is stabilization/alignment of the infrastructure layer; prefer extending via `InfrastructureApi` + engine managers instead of ad-hoc listeners.

Mob behavior subsystem (`infrastructure.mob`, Phase 3 axis): modules register per-entity-type `MobProfile`s (`MobBehaviorApi` via `PluginContext#mobBehaviorApi()`) � ordered `BehaviorAction` entries with interval seconds plus optional `BehaviorContext` predicates; at most one action fires per entity event with the reference-mod odds semantics `1/(intervalSeconds * checksPerSecond)`. The `MobBehaviorEngine` runs a budgeted, distance-gated loop (`MOB_BEHAVIOR` in settings.mp.yml: interval, stagger buckets, scan radius, per-run millis budget, hard block-edit cap): players' surrounding loaded chunks are scanned with alternating parity, entities dedupe through a fastutil long set and stagger by id-bucket, per-evaluation state lives in a reusable `BehaviorContext` (no statics), world edits route through `trySetBlock`/`tryBreak`/`trySpawn` under a run-scoped `MobEditSession` grant (capped by `MAX_BLOCK_EDITS_PER_RUN` and `MAX_ENTITY_SPAWNS_PER_RUN`; a build that outlives its evaluation asks for its own grant through `openEditSession(editBudget, spawnBudget)`, always clamped to the same caps), scenario conflicts are settled by anchored activity claims (`claimActivity(id, anchor, radius, durationTicks)`, `activeActivity`, `clearActivity`) that both keep a mob off other profiles and hold it inside its confinement area, and `BehaviorTelemetry` surfaces counters. The engine is lazy (starts on first registration, shut down on Core disable). Bundled actions (`infrastructure.mob.action`): `EatPlantsAction`, `GrowPlantsAction` (vanilla bonemeal), `PlantSaplingAction` (biome-matched, spacing-checked), `TorchPlaceAction` (block-light gated), and `JourneyToStructureAction` (Builder + `Callbacks{onNight->boolean, onArrival, onNotFound}`) - the long-range scenario primitive: structure found through `StructureLookup` on a search cooldown, destination normalised to a standable cell by `GroundProbe`, walked leg-by-leg by `JourneyRunner` (stall detection, detour retry, leash), crew cohesion through `MobCrewService` (a shared formation point - `crewRally` - that advances along the route only once the whole crew has reached it, each member handed one bounded step toward it by `crewRejoin`, so a waypoint beyond the mob's own path range never stalls the march; stragglers are walked back *before* the crew halts, so a night camp always gathers the whole crew), night rest and camp callbacks under an exclusive anchored activity claim (a claim remembers the owning profile's priority, so a strictly higher-priority scenario may take the mob over and a lower-priority one never can), day/night read through `infrastructure.mob.WorldTimes` (one owner for the sky's semantics), and runtime-only journey/crew state (never PDC, so a restart cleanly forgets a half-finished march). Navigation is `infrastructure.mob.navigation.MobNavigator` (Paper `Pathfinder` first, reflective NMS fallback on Spigot through the mob's own `NavigationAbstract`, resolved from its live handle class so a loosely-declared `getHandle()` like `CraftVillager`'s still yields navigation/look/Brain; never teleports or spawns). Every accepted request also turns the vanilla look control toward the destination, because cleared goals leave nothing else to rotate the body; a request refused while the mob is airborne is retried on the caller's cadence, not treated as unreachable. Long-range movement is follow-range aware (`MobAttributes.pathRange` clamps every journey leg, so a villager's 16-block follow range is never handed a 32-block waypoint), Paper paths open doors and float, and a journey may hold a bounded plugin chunk ticket (`ChunkLease`) for the leg it is walking. Each leg is routed, not drawn straight: `infrastructure.mob.route.RoutePlanner` samples the straight line first (a handful of block reads; clear ground returns the leg unchanged) and only on obstruction runs a bounded A* over a 25×25-cell window (2-block cells, ≤256 expansions, octile heuristic, water crossable-at-a-price, up to four-block drops, lava/cliffs blocked, ≤24 searches per engine step across all mobs), then normalises the waypoint through `GroundProbe`; the plan is segmented (rolling window, replanned each leg), never guesses at unloaded terrain, and a stall earns exactly one full reroute before `JourneyRunner` reports `STUCK`. Multi-stage scenarios are `infrastructure.mob.pipeline.MobPipeline` definitions (immutable, shared; per-mob state in `PipelineContext`'s blackboard) attached through `MobBehaviorApi.assignPipeline/pipelineOf/pipelineSnapshot` and ticked by `MobPipelineEngine` under `MOB_BEHAVIOR.MAX_PIPELINES_PER_RUN`, with per-stage timeouts, exclusive `pipeline:<id>` activity claims (the ordinary evaluator skips owned entities), bundled `LocateStructureStage`/`JourneyStage`/`SettleStage` stages, and takeover detection when a higher-priority action claims the mob; `SettlerPipeline.builder(id)` assembles the locate → travel → settle → build recipe (cached bell-anchored lookup, routed march, a standable home spot within a radius stored as `<destinationKey>#home`, module build callback), so a settler state machine is a pipeline definition rather than hand-rolled phase counters. Crew shape is `infrastructure.mob.group.SquadManager` (per crew identity: `Formation` NONE/COLUMN/LINE/WEDGE/RUSH/PINCER/SURROUND slot offsets in the crew's own forward/lateral frame, `SquadRole` LEADER/TANK/BREAKER/FLANKER/SUPPORT/SNIPER/DISTRACTOR biases, spacing) applied inside `MobCrewService.rejoinWaypoint`, plus `FlockSteering` separation (capped sideways push, stable overlap split) so members do not stack on one block; `JourneyToStructureAction.Builder.formation(...)`, `BehaviorContext.setCrewFormation/setCrewRole` and `MobBehaviorApi.squads()` expose it, and crews with no formation or role cost nothing (the plain formation point is returned on the first check). `StructureLookup` anchors every found structure to a walkable point through `StructureAnchor` (a village's loaded bell, else its bed centroid, else a standable cell). `MobBehaviorApi.forceFire(plugin, entity, ignoreConditions)` is a main-thread testing hook that bypasses the odds gate and returns a per-action `BehaviorFireResult` (FIRED / DECLINED / CONDITION_FAILED). `examples/mineplus-mobfun` ("MobFun") is the showcase module: Grazer Cow, Grazing Sheep, Reforesting Pig, Lamplighter Villager, Florist Bee (module-side `PlantFlowerAction`), Golem Guardian + Frost Builder Villagers (module-side `GolemSummonAction`, `inDanger` condition: raises the 3-block column block-by-block over scheduled ticks into a real iron/snow golem that instantly targets the menace - every staged write goes through one `openEditSession(6,1)` grant and `session.spawnMob`, never raw `setBlockData`, and the whole column is re-verified before any of it is cleared, so an interrupted build leaves a column and never a half-cleared site; per-builder PDC cooldown + one-golem cap, and the builder is PDC-tagged so the pilgrim journey never marches it away), Necromancer Witch (module-side `NecromancerRaidAction` starts the village-raid pipeline - locate the nearest village through `LocateStructureStage` (bell-anchored), march through `JourneyStage`, then `NecromancerRaidStage` rings the bell, retargets the surviving horde onto the nearest villager, waves biome-matched minions through `context.openEditSession(0,3)`/`session.spawnMob`, and ends when the village is empty or the raid ceiling is reached; per-witch PDC cooldown paces raids - while idle she still runs the ambient `SummonMinionHordeAction`: terrain-adaptive ring-scan spawn spots within a 24-block leash of the witch, every minion through `context.trySpawn` under the run's spawn budget, with per-spot clearance clearance-matched biome horde (husk/stray/drowned/cave spider), skeleton-horseman archer every 5th raid, whole-horde target sync, potion retaliation vs close golems, retreat hops behind her own screen; per-witch summon cooldown + horde cap), and Pilgrim Villager (the Core's `JourneyToStructureAction` with a module-side `PilgrimCamp` callback: wasteland villagers locate the nearest village (64-chunk search radius) and march there as a cohesive `Formation.WEDGE` crew; at night the crew is walked back to its focus before it halts, then the leader raises one shared camp (campfire plus a contiguous bed row, one bed per crew member, both halves of every bed verified before either is written, every edit under the run's budget and retried within the same night if the budget refused) and holds until dawn; they celebrate on arrival, and `/mobfun status` prints the Core's `journeySnapshot()`/`crewSnapshot()`/`pipelineSnapshot()` plus `squads().snapshot()` and the live activity claims) with `/mobfun status|<id> on|off|toggle` plus a test bench � `/mobfun spawn|fire <id> [force]` (spawn-and-force testing) and `/mobfun despawn`.

Custom mobs (`infrastructure.mob.custom`, a peer axis to mob behavior): a custom mob is a vanilla base `Mob` carrying a Mineplus identity, its own visual model, attribute overrides and its own behavior profile, never a new entity type. `PluginContext#customMobs()` returns `CustomMobApi`: modules build a `CustomMobDefinition` (`builder(id, baseType[, CustomMobModel])` + `displayName`/`showName`/`persistent`/`hideBaseWhenRigged`/`canPickupItems`/`attributes`/`behavior`/`spawnConfigurator`), `register(owner, definition)` it (owner-scoped: same id from a different owner is a conflict, same definition is idempotent, `unregisterAll(owner)` is the module-disable path), then `spawn(location, id)` — nothing is registered until a module asks for it. Identity is PDC (`custom_mob_id`) + a scoreboard tag + an in-memory UUID->id cache, and the manager implements `MobIdentityResolver`, which the engine consults before dispatch, so custom profiles live in `profilesByCustomId` and are never visible to vanilla mobs of the same base type (nor does a custom mob match a `MobProfile.builder(EntityType)` — `forceFire` resolves the same way). Every spawn and chunk restore re-applies identity, attributes (health clamped to the new maximum, not refilled) and `MobAiIsolation.isolate` (goal/target selectors cleared, AI left enabled so the navigator still ticks the vanilla walk), so a custom mob runs no vanilla AI and every action comes from its profile; a definition with no behavior consumer gets an idle profile. Unknown tagged ids stay isolated and are removed on chunk load only once at least one definition exists (`CUSTOM_MOBS.REMOVE_UNKNOWN_ON_LOAD`), and a first-registration sweep restores already-loaded mobs after a restart. Rendering: `CustomMobModel.vanilla(type, png)` reuses a published vanilla descriptor (texture-only extension), `builderFor(type, png)` and `builder(w, h, png)` author parts (`MobPart` absolute pivots + `Role` HEAD/BODY/LEG_*/STATIC, `MobBox` from/to/texOffs in vanilla model pixels); `MobRigAssetWriter` compiles it into pack assets (one texture, one item model + item definition per part with vanilla box-UV -> element face windows), keeping every element inside the client's -16..32 px item-model window: a slight overshoot is shifted, a part larger than 48 px on an axis is split into deterministic pieces (`<part>_p2`, ...) that each get an `ItemDisplay` and are reassembled by the pose pass, so authoring never has to respect the window. `MobRigRenderer` hides the base entity and presents each part/piece as an `ItemDisplay` with an `item_model` component, posed from body yaw/pitch with a lazy, self-retiring task, with the yaw frame `R_y(180 - bodyYaw + yawOffset)` matching the authored -z front to the entity's facing and the head bone following head yaw + look pitch; without the pack the base entity simply stays visible. Cost is bounded by `CUSTOM_MOBS` in settings.mp.yml (`ENABLED`, `RENDERING`, `RENDER_INTERVAL_TICKS`, `RENDER_INTERPOLATION_TICKS`, `RENDER_DISTANCE`, `MAX_RIGGED_PER_WORLD`, `REMOVE_UNKNOWN_ON_LOAD`). `AttackNearestAction` (Core, `infrastructure.mob.action`) is the bundled hostile action: sticky target (60 ticks), creative/spectator skipped, throttled re-path, line-of-sight checked strike through `DamageTransactions.apply` plus knockback and sounds. MobFun registers the Evil Pig (`mobfun:evil_pig`, `EntityType.PIG`, `CustomMobModel.vanilla(PIG, png)` with the embedded `mobs/evil_pig.png`, attributes, and `AttackNearestAction`) as the minimal custom-mob showcase, spawnable through the same `/mobfun spawn|fire evilpig [force] | despawn` test bench. A second custom mob, the Villager Soldier (`mobfun:villager_soldier`), is imported from a Blockbench `.bbmodel` through `BedrockMobModel` (outliner-as-rig via `partsFromOutliner()`: group pivot, rest rotation and parent become a `MobPart` bone) on a villager base and hunts hostile mobs (`Enemy` targets) at spear reach; its `animation.walk`/`animation.idle` clips are blended by movement speed. A third, the Woodland Trickster (`mobfun:woodland_trickster`), adds a one-shot `animation.attack` clip: `MobRigRenderer` resolves walk/idle/attack by name, plays the attack clip on the mob's melee hits (its own `EntityDamageByEntityEvent` listener, or `MobRigRenderer#playAttack` for module timing) as an overlay that hands the parts back to walk/idle when it ends, and applies group rest rotations in the rig's y-up space. Full guide: `docs/custom-mobs.md`.

Combat & gameplay support subsystems (Phase 4 axis, Core-owned so no module re-implements them):
- `infrastructure.combat`: `Ballistics` is the shared round simulation (one stepped pass per `INTERVAL_TICKS` over live rounds; spread, gravity, drag, range falloff, penetration, ricochet, headshot, tracer/impact FX emitted through `ParticleFx`; over `MAX_ACTIVE_ROUNDS` a shot degrades to a single instant trace instead of queueing, counted as `degradedShots()`), driven by `BallisticProfile` (builder: damage/velocity/gravity/drag/range/spread/pellets/falloff/minDamageFraction/headshot/penetration/ricochet/hitboxExpansion/tracerSpacing/particles/sparks/sounds; tolerant particle and sound names) and `ProjectileHandler` (all-default callbacks: `allowTarget`, `onLaunch`, `onEntityHit` returning `false` withholds damage, `onBlockHit`, `onExpired`; callbacks run on the server thread inside the simulation step, so hit code needs no scheduling). `DamageTransactions.apply(victim, amount, attacker)` is the attribution seam - module-computed damage marked so the same swing is never counted twice, with `inProgress()` as the re-entrancy flag a listener checks. `CombatSettings` parses `BALLISTICS` + `PARTICLE_FX`.
- `infrastructure.input.HeldItemInput`: the single listener set every module shares. A module implements `HeldItemHandler` (`owns(stack)`, `owns(stack, holder)` for per-player opt-out so a disabled carrier stays fully vanilla, `onPress`, `onRelease`, `onSwapHands`, `suppressVanillaMelee`, `freezeVanillaInteractions`) and attaches it once; the service routes presses, swallows the vanilla swing, and freezes place/mine/trade/ride while the item is owned. Probing (`Class.forName`) keeps the Paper-only seam from linking on Spigot. The press stream is a gesture, not a packet: a modern client answers a click on a block with two use packets and keeps sending them while the button is held, so `TriggerState` folds them - a press inside the 150 ms click window of the previous one continues the same click, a release always ends it, and `freshPress()` tells a handler whether this is a new gesture (fire once) or a continuation (keep an automatic weapon firing).
- `infrastructure.fx`: `ParticleFx` (CRITICAL/AMBIENT per-tick budgets, self-healing 50 ms window, never throws - a refused particle counts as dropped) and `Sounds` (enum constant, vanilla key or custom namespace with a vanilla fallback; an unresolvable custom event can never unwind the caller's action). Both are handed out by `PluginContext` (`particleFx()`, plus `ballistics()`, `heldItemInput()`, `mobBehaviorApi()`).
- `infrastructure.registry`: `ItemState` (typed PDC value on an `ItemStack`, plus the per-stack identity tag) and `ItemMagazine` (countable rounds live in memory while the stack is held, flushed as one silent PDC write when it leaves the hand - rewriting a held stack per shot replays the client equip animation and spams slot packets; tags only ever stamped on single-item stacks because a stack of two is a pair of clones that would share one magazine). `pack.item.ItemFrames` carries the idle/loaded/reload/fire frame math for `item_model` presentation and `pack.item.ItemFrameWriter` puts one state on the stack: the modern dispatch reads the `custom_model_data` component's float list, the legacy representation reads the integer, so both are written (both accessor spellings are probed - the API declares a primitive getter and a boxed setter) and the pack strips the UTF-8 BOM that makes a model load as a missing model.

Module layer (features live outside the Core): `examples/mineplus-fun` is the canonical reference module — a separate plugin (`depend: [Mineplus]`) containing the Juicer (recipes/GUI/custom items), the Cannon (conditional interaction: torch fires, else opens menu; persistent TNT ammo in `stateData`; rotation-aware placement via `createMultiBlock`/`placeMultiBlock`), the Gear (redstone-driven bbmodel clip animation with chain reaction through `AnimationApi`), the Wine tasting flight (texel surface baking showcase: five vinery bottles whose 16x16 sprites are reconstructed from vanilla palette blocks with zero resource pack; converted `java_block` bbmodels + per-model `.meta.json` opt-ins, `/wine place [variant]|flight|remove|clear|status`), the Cabinet (model-as-state storage: two levels where level 1 renders the closed acacia cabinet and level 2 the open one; right-click swaps to open + shows an 18-slot `AbstractMachineGui` whose `onClosed` swaps back; contents persisted as Base64 `ItemStack#serializeAsBytes` in `stateData` and dropped on break/remove; per-model `.meta.json` plate-budget opt-ins because the vinery wood sprites are gradient-heavy; `/cabinet place [texel|resourcepack]|remove|clear|status` � `texel` places the virtual/texel `cabinet`, `resourcepack` places the pack-block twin `cabinet_pack` (same models, `renderBackend: pack` + `renderKind: block`) for A/B testing the two render axes), and the Pack Showcase (`fun:strad_wine` pack item from the Wine feature's assets; `/packshowcase [status]`), and the Alchemy Table (the pack block showcase: a `renderBackend: pack` + `renderKind: block` multiblock level rendered as one `BlockDisplay` through an allocated `note_block` carrier state, geometry serialized in block space and textures from the same PNG pipeline; `/alchemy place|remove|clear|status`). Module internals follow the `ModuleFeature` lifecycle contract: features implement `id()`/`onEnable()`/optional `onDisable()`+`command()`; the bootstrap starts all features (exception-isolated per feature), performs exactly one coordinated `reloadAll()` for the whole module, then registers the features' commands; teardown runs in reverse enable order. Its `DEVELOPMENT_PROMPT.md` is the authoritative module-building recipe (verified Core behavior, GUI patterns, API traps). Keep the Core pristine: no feature code, no feature resources, no feature commands. Two further modules sit on the gameplay axes: `examples/mineplus-gun` ("MineplusGun") keeps only weapon definitions/config, the event-driven weapon runtime (sessions, pose machine, HUD dedupe), Vault shop and `WeaponFrames` file discovery - a gun folder's model names (`<id>_idle`, `<id>_primed`, `<id>_loading_N`, `fire_N`, `scope_in|hold|out`, `cycle`, `equip`) classify themselves, so every animation is optional and adding a gun is a folder plus a config entry, never a frame list - with the projectile loop, held-item routing, damage attribution, magazine persistence and particle/sound budgets all owned by the Core. Its controls are right-click to fire (one Core-folded press per click, sustained `AUTO` from `TriggerState.held()`), left-click to toggle the scope and otherwise fully swallowed, and swap-hands (F) to reload, with an empty gun reloading itself; recoil is modeled as dispersion because a server cannot rotate a modern client's view. and `examples/mineplus-mobfun` ("MobFun") keeps only content-side `BehaviorAction`s and journey callbacks (Grazer Cow, Grazing Sheep, Reforesting Pig, Lamplighter Villager, Florist Bee, Golem/Frost builders, Necromancer Witch, Pilgrim Villager) plus its `/mobfun status|spawn|fire|despawn` test bench, with scheduling, navigation, journeys, crews, claims and world-edit budgets owned by the Core mob engine.
